# bunkiten v1.10.1

本版给 v1.10.0 收尾，三件事：把「服务目录发布 → 你那边可见」的窗口从**最长一天多（且必须重启）**压到**约 5 分钟 + 6h，打开一次设置屏就刷新**；把 Windows 侧的代码签名从**写死关闭**改成**就绪**（证书一到即自动生效，不改代码不改配置——**但这一版仍然是未签名产物**）；清掉三项依赖升级里唯一会红的那个（**jsdom 钉回 30.0.x**）。旧存档、旧导出包、旧设置、已存的凭据与服务地址一律兼容，无需任何迁移。

## 服务目录更新窗口收窄（ADR-0020 的「修订」段）

原先的窗口是三项相加：jsDelivr 边端缓存（可达 12h）+ 24h 本地 TTL + **必须重启**才生效——从你改完发布源到玩家下拉里出现，最长一天多。三项一起压：

- **两个发布源并行抓、按 `updatedAt` 取最新**：此前是「先主后备、首个有效即止」，而可达性更好的 jsDelivr 一能用就永远压住 GitHub raw——实测两源内容一致（同 `updatedAt`、同 27 条），但 raw 回 `cache-control: max-age=300`（分钟级）、jsDelivr 回 `s-maxage=43200`（边端 12h），于是「谁先答话」决定了新鲜度。现在两个源**同时**抓（`Promise.allSettled`），各自过校验后按 `updatedAt` 比大小取最新（缺失/解析不出当最旧；完全并列取靠前源）。定位是分工的：**GitHub raw 主新鲜度，jsDelivr 保可达**。`BUNKITEN_PROVIDERS_URL` 覆盖时保持单源语义（测试与镜像要确定性）。
- **TTL 24h → 6h**（`CATALOG_TTL_MS`）：与常用 CDN 的边缘缓存同量级，本地这层不再主导整个窗口。
- **`/api/providers` 读路径改 stale-while-revalidate**：新增 `revalidateCatalog`，读接口**先立即回当前目录**（不让你等网络），再 fire-and-forget 触发一次后台刷新——永不抛、不阻塞、进程内单飞；未过期或 `BUNKITEN_DISABLE_UPDATE=1` 时一次网络都不打。于是**长开着的应用不必等下次重启**：打开一次设置屏就刷新。

收窄后的窗口算式：`min(各发布源 CDN 缓存) + TTL(≤6h) + 一次抓取延迟`，触发点是**启动**或**过期后的下一次 `GET /api/providers`**。raw 可达时 ≈ **5 分钟 + 6h**（对比原文的「12h + 24h + 重启」）；只有 raw 不可达、退到 jsDelivr 时才回到 ≤12h + 6h。

**离线或校验失败照旧回落内置表**（`source:"bundled"`），安全边界一条没松：远端**只喂下拉候选**，绝不据此改写你已存的服务地址、密钥与模型；发布源里的地址只收 `https`（例外只有本机 `localhost`/`127.0.0.1`）；整包校验失败即弃、只搬白名单字段，单条坏只丢那一条。

## 签名就绪（仍需你出手）

- **Windows 侧此前是「硬关」**：`win.signExecutable: false` 不是「没证书就跳过」，而是 `signIf()` 见到它就 `return false`——**证书配齐也不会签**，且把 NSIS 安装器与卸载器一起堵死，等于把条件化的路封了。
- **现在条件化**（v26.15.3 源码实证）：`WIN_CSC_LINK` / `WIN_CSC_KEY_PASSWORD` 存在即签名 + RFC3161 时间戳（应用 exe、asar 外的 exe/dll、NSIS 安装器与卸载器一并签）；**缺则与今天完全一致**——没有 `cscInfo` 时 electron-builder 只打一条 debug「no signing info identified, signing is skipped」就跳过，不 fail；而 PE 资源编辑是**另一条**路径（`signAndEditResources()` 先写图标/版本串再 `signIf()`），未签名产物的图标与版本元数据照写。`release.yml` 的 win job 与 mac 同款：注入两个变量、**空值先 unset**（secrets 缺失时注入的是空串，空串会被当成「证书配了」），并刻意不传 `CSC_LINK`（别让 Apple 的 `.p12` 进 Windows 这条路）。**证书一到即自动生效，不改代码、不改配置。**
- **新增 `docs/RELEASING.md`**（维护者向）：两个平台的证书**要买哪种、怎么导出、怎么转 base64、进哪个 Secret**；**开启后会发生什么**——mac 首次打开不再被拦、**自动更新这才可用**（且这是**单向门**：一旦某个版本签名发布，后续必须继续签名），Windows 侧是 SmartScreen 的 EV/OV 差别与带时间戳的意义；**怎么验一次发布**——`codesign` / `spctl` / `xcrun stapler` / `signtool verify /pa /v`，以及应用内 updater 的**成对**真验收（未签名→未签名只在 win 上能更新，mac 要签名→签名才通）。另附「我们不做的事」：证书不入库、不自签冒充、不教玩家关 Gatekeeper/SmartScreen、不为试签名重跑已发布 tag、不做云签名。
- **这一版仍然是未签名产物**——没有证书就照旧。mac 首次打开需右键 → 打开，Windows 会有 SmartScreen 提示；**未签名的 mac 包不能自动更新**。本机交叉打包（`npm run dist:win`）已实测走的是未签名路径：产物无证书表、`app-update.yml` 里没有 `publisherName`，图标与版本元数据照写。

## 依赖与钉版

- **三项 minor 升级**：framer-motion `^13.3.0 → ^13.4.0`、lucide-react `^1.46.0 → ^1.47.0`、electron `^44.3.0 → ^44.4.2`（含 `package-lock.json`）。
- **jsdom 钉回 `~30.0.1`**：30.1.0 让 `tests/ui.test.tsx` **6 条用例红**（5 条走 Radix ⋯ 菜单的改名/导出/导入 + 1 条音效槽位兜底超时，同一文件 144 条通过）。**二分证据**（同一批四个升级）：四个一起装 → 6 failed；jsdom 回退 30.0.1（framer-motion 13.4 留着）→ **150 passed**；framer-motion 回退 13.3.0（jsdom 30.1.0 留着）→ 仍 6 failed。所以病根只在 jsdom，其余三项干净可用。
- **已加 dependabot `ignore`**（`>=30.1.0 <30.2.0`，免得被同一批再提上来），**复访条件写在 `tests/setup-react-act.mjs` 顶部**（含二分表、未证实的嫌疑方向，以及「jsdom 30.2+ 修了这 6 例、或我们把这些用例适配到新事件行为后，删 ignore、放宽范围、重跑确认 150 passed」）。

## 工程与验证

- **用例口径**：单测 + 集成 **560+ 例**（实际 597），UI e2e **21 个 spec / 44 条**；契约 lint（协议常量真源断言、发布源与真源深等、GUI 不许自带第二份服务表）同批同步。
- 本轮测试补的是窗口收窄本身的可证性：单测覆盖「两源取新 / 只有备源有效 / 两源都失效 / 缺时间戳当最旧与并列取前者 / TTL 边界 / revalidate 的零请求·真抓·单飞·永不抛」，集成覆盖「预写过期缓存 → GET 先回缓存态再轮询到 remote」与「预写新鲜缓存 → GET 后 mock 源零请求」。

## 已知限制

- **真出图 opt-in 跑有代价**：需要本机已登录 grok CLI + 能出网 + 图片服务凭据，且**真的花一次对话与一张图**（「测试连接」的图片侧同理，GUI 里已明说）。
- **未签名的 mac 包不能自动更新**：Squirrel.Mac 要求新旧包签名一致，而本版发布的正是不签名产物（升级走手动下载 Release 产物）。要开签名见 [RELEASING.md](../RELEASING.md)；Windows 侧未签名只影响 SmartScreen 提示，不影响更新。
- **在线目录仍有窗口期**：目录更新是尽力而为的后台动作，窗口已收窄到 `min(各源 CDN 缓存) + 6h + 一次抓取延迟`——不是实时；raw 不可达、退到 jsDelivr 时回到 ≤12h + 6h。抓不到就继续用内置表，**这不影响任何已存凭据**。
- **自备 key 明文落盘（v1.10，刻意取舍）**：`~/.bunkiten/credentials.json` 是明文 + 0600，本机磁盘加密（FileVault/BitLocker）是这里的第一道防线；加密存储（keychain/密钥派生）留给后续版本（见 ADR-0019 的「被否决的备选」）。
