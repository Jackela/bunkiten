# 删除进回收站（state/trash/），直删只留作 EXDEV 回退

世界线的「删除」原来是 `fs.rmSync` 整目录直删、画廊素材是 `fs.unlinkSync` 单文件直删：一局几十轮的 state/summary/story-tree 与全部 history 快照、或引擎画出来的立绘/背景，点两下确认就不可逆地没了——个人项目没有服务端备份与版本历史，误删的代价全部落在玩家（常常就是开发者自己）身上。裁决：删除一律先挪进 `state/trash/`（`moveToTrash(root, ...rel)`，server 内唯一入口），项命名 `<删除时间戳ms>-<随机4字符>-<原名>/`（随机后缀规避同一原名反复删除的撞名），世界线目录与素材文件同款。选 rename 而非复制后删除：同卷 rename 原子，要么整体进 trash、要么原样不动，不存在「删了一半」的中间态；trash 长在 `state/` 下，天然不在任何扫描面内（`scanPresets`/`scanPresetAudio`/`listAssets` 只看 `presets/`，`listWorlds` 与快照只看 `worlds/` 与 `index.json`，`migrateLegacyState` 只读 state/ 本层 `*.md`），挪进去的东西等于从游戏里消失，不需要各扫描点逐一排除。**回收站是尽力而为**：跨设备挂载（EXDEV）等 rename 失败时回退 `rmSync` 直删并在返回值里带 `fallback:"purged"` 标记——删除操作本身不能因为 trash 失败而失败，宁可丢回收站也不能丢「删除」语义（回退的 rmSync 也失败则原样抛出，交给调用方按删除失败报 500）。恢复只走手工文档（`state/README.md`「回收站」一节：世界线目录挪回 `state/worlds/<id>/` 并在 `index.json` 手工补条目，素材剥掉 trash 前缀挪回 `presets/<id>/assets/`）。代价：其一，磁盘占用只增不减（**不自动清理、不设上限**，回收站纪律交给玩家手动管理——自动清退必然引入「保留几天」这类拍脑袋参数，且清错一次就回到了直删）；其二，世界线恢复要手工补 index.json 条目（索引是唯一列表真源，删除时先移除条目再挪目录，两步无法对随手恢复做增量索引）；其三，没有恢复 UI（`existsSync` 语义、删除确认文案、世界线列表都以「删掉即消失」为前提，恢复 UI 要引入按类型剥前缀、索引回补、重名冲突三套规则，超出「误删有后悔药」这个最小诉求）。客户端只在删除成功的提示文案里说明去向（「已移入回收站（state/trash/ 可手工找回）」），交互不变。被否决：继续直删（误删不可逆）、复制后删源（两步之间崩溃会留下双份或半份）、trash 放进 `state/worlds/` 下靠扫描排除（每个读 worlds 的点都要记得排除，漏一处就「幽灵世界」）、自动过期清理（见上）。
