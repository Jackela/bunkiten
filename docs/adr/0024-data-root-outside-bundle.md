# 数据根移出应用包（BUNKITEN_DATA_ROOT / userData / 迁移 + seed-sync）

打包态此前把**可写数据**（`state/`、玩家侧 `presets/`、`.shell-session.json`）和只读内容（`.grok/`、`app-dist`、随包剧本）放在**同一个根** `resources/game` 里，而那个根长在 `.app` 内部。macOS 的覆盖安装是**整包替换**——新 `.app` 盖掉旧的，`Contents/Resources/game/state/` 连同玩家一局的 state/summary/story-tree/history 一起蒸发。v1.6 的发布说明还写着「进度不会被覆盖安装清掉」（当时把 `state/` 放在 asar 外就当成了安全），**那是错的**：asar 外只保证「进程写得进去」，不保证「升级后还在」。玩家（常常就是开发者自己）装一次新版即丢档，且事后无法挽回。

裁决：**把可写数据根从 bundle 里搬走**。其一，`electron/main.js` 在打包态把数据根定为 `app.getPath("userData")/game`（macOS 的 `~/Library/Application Support/Bunkiten/game`，Win 的 `%APPDATA%/Bunkiten/game`），经 **`BUNKITEN_DATA_ROOT`** 注入 env（测试与回退可覆盖）；**dev 不设这个 env**——`server/config.mjs` 的 `DATA_ROOT` 回落 `GAME_ROOT`，写路径仍是项目根，行为与改动前一字不差。`config.mjs` 新增 `DATA_ROOT` 常量，`WORLDS_ROOT`/`SESSION_FILE` 与资产写路径全部切到它；`GAME_ROOT` 退化为**只读内容根**（`.grok/`、`app-dist`、随包剧本种子）。引擎的 cwd 是**数据根**（SKILL 里的 `state/…`、`presets/…/assets` 都是相对路径，按 cwd 落盘），而 `--plugin-dir`/CODEX_HOME 的 skill 源仍指只读内容根——所以 `server/acp-server.mjs` 的 `buildAcp` 在这里把两个根**分家**：`prepareSpawn` 收 `GAME_ROOT`、`createAcpSession` 收 `DATA_ROOT`。

其二，`server/data-root.mjs` 的 `prepareDataRoot({dataRoot, bundleRoot, migrate})` 在**每次启动**（且 `import acp-server` **之前**，因为 `config.mjs` 在模块加载期就读 env 定 `DATA_ROOT`）跑两条幂等职责：① **一次性迁移**——数据根那一片（`state/` 与 `presets/` 各自独立判定）还空着、bundle 里有货 → 整树**复制**（**不删源**，失败保底：旧 bundle 里的数据原样留着）；`.shell-session.json` 缺则补。② **seed-sync**——bundle 的 `presets/` 里每个文件：数据根缺就补拷；已有且**内容仍等于种子哈希**（即玩家没改过）就随版本更新覆盖；玩家改过的一律不碰。种子记账在 `<数据根>/presets/.seeded.json`（`{version:1, files: {rel: sha1}}`），迁移复制出来的文件在同一步登记进清单——漏了这步会同时坏两件事：升级新增/改过的官方 `preset.md`/`cover.jpg`/`audio/` 永远停在旧版，且内置剧本会被当成玩家自有剧本放行删除（删掉下次启动又补回来）。`isSeededPreset(dataRoot, id)` 就是给删除入口用的判据。

其三，进程侧的三条护城河：`requestSingleInstanceLock()`（**必须在 import server 之前**——第二个实例不迁移、不 seed、不抢 7800-7810 端口、不开窗，直接把已有窗口拉到前台后退出；两个进程同时跑会抢端口并并发写同一份数据根）；启动失败 `dialog.showErrorBox`（消息给「可能已有实例在运行 / 端口 7800-7810 被占」两条最可能的诊断 + 数据目录）；`mirrorConsoleToFile(dataRoot)` 把主进程与 acp-server 的 console 追加进 `<数据根>/logs/app.log`（dev 不接，免得往仓库写文件）。

代价与前提：其一，**打包态首启多一次整树复制**（已有旧档的玩家升级时一次性付，`state/`+`presets/` 大时是秒级 IO，且迁移只复制不删源，失败不挡启动）。其二，**官方 preset 的更新策略变复杂**：随包内容不再是「永远最新」，而是「玩家没改过才随版本更新」——这正是 seed-sync 哈希清单存在的原因，也是它唯一的用途；玩家改过的官方 `preset.md` 从此会一直保留（升级不会静默抹掉他的改动），代价是他要自己重看新版的 diff。其三，**两个根要一直分得清**：改路径的代码要问一句「这是只读内容还是玩家数据」——写错根的把玩家数据写回只读 bundle 即「下次覆盖安装丢档」，读错根即「看不到玩家的档」。其四，`.shell-session.json` 迁到数据根后，旧 bundle 里那份只在首启补拷一次（缺才补）。被否决：**继续把数据放 bundle 内**（正是要修的问题——覆盖安装吃档，且发布说明已经骗过一次）；**把 `state/` 写进 userData 但 `presets/` 留在 bundle**（玩家的生成素材、导入与创作剧本本来就写进 `presets/`，拆一半等于半个问题还在）；**首启把整个 bundle 的 `game/` 复制一份**（`.grok/` 与 `app-dist` 是只读内容、每个版本都换，复制它们等于把版本漂移固化进数据根）；**用符号链接把 userData 指回 bundle**（跨卷、跨平台行为不一致，且覆盖安装换掉目标后链接悬空）。相关：`docs/ARCHITECTURE.md`「两种运行形态 / 打包布局 / 已知限制」、`.github/workflows/ci.yml` 的 `packaged-win` 与 `tests/e2e-packaged/`（数据根注入 + 迁移用例）。
