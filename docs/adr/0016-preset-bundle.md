# 剧本导出包 bunkiten-preset v1（JSON + base64，上限只挡导入端）

剧本分享此前只有「拷整个 `presets/<id>/` 文件夹」一条路：哪些文件该带走、带走的包能不能原样导回，全凭人肉记忆，与世界线导出包（`bunkiten-world`）不对称。裁决：剧本导出包 `<id>.preset.json`（`format:"bunkiten-preset"`、`version:1`），包体 = `preset.md` 全文 + `assets`（`jpe?g`，preset 根的 `cover.jpe?g` 也在内）+ `audio`（`AUDIO_EXTS`），二进制一律 base64——**JSON + base64 与世界线导出包对称、零依赖**（tar/zip 要么引依赖要么调系统二进制，跨平台行为不可控）。导出收文件面与导入校验面严格互为镜像：导出时子目录、不认识的扩展名与 0 字节文件一律跳过，保证导出来的包一定能原样导回。50MB body 上限**只给导入端点**（`POST /api/presets` 给 `readBodyText` 传可选 `maxBytes`，其余调用点的 5MB/413 语义一字不动）——导出侧刻意不设上限：上限的真实语义是「挡住导不回去的包」，导得出来导不回去才难堪，所以只挡进口不挡出口。导入校验四道闸，任何一项不合法**整包拒绝、不写半个剧本**：文件名单层（无路径分隔符、不含 `..`、无首尾空白）+ 长度 ≤200（UTF-8 下 CJK 每字 3 字节，>200 字符必然越主流文件系统单名 255 字节上限，`writeFileSync` 会抛 ENAMETOOLONG）+ Windows 保留名拒绝（CON/PRN/AUX/NUL/COM1-9/LPT1-9，按去扩展名 stem 大小写不敏感——`CON.jpg` 在 Windows 上写不进、会被系统吞掉）+ 严格 base64 round-trip（Node 的 `Buffer.from(str,"base64")` 会**静默丢弃**非法字符，重新编码与原文比对才能拦住截断/夹私货的形态）；另限解码总量 ≤50MB。落盘走「临时目录（`presets/.tmp-<id>-<随机>`，点前缀就算极端残留也进不了轮播）写全量 → 同层 `rename` 进位」：写盘/rename 的任何 IO 异常清理临时目录后返回 error 而**绝不抛出**——server 在 Electron 主进程内同进程运行，`readBodyText` 的回调链上没有兜底，异常冒泡即 uncaughtException、整应用闪退（v1.7 审查实证：临时目录 + rename 的原子性修复正来自这条发现）。重名加 `-2`/`-3`（与 `importWorld` 同款循环，占用以磁盘目录为准——presets 没有索引文件，`scanPresets` 扫的就是目录）且**改写 frontmatter id 行为落地 id**：`scanPresets` 按 frontmatter id 进轮播，不改写就是「目录 `demo-2`、轮播里还叫 `demo`」的重复卡带，后续美术/音频也会按轮播 id 落错目录。代价：其一，50MB base64 JSON 在导入瞬间的解析内存峰值（本机回环、个人工具，可接受）；其二，落地剧本的 frontmatter id 可能与包作者写的不同（重名改名的直接后果）。被否决：tar/zip 打包（引依赖，见上）、导出侧设上限（见上）。
