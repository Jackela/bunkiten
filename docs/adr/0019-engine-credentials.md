# 引擎凭据（GUI 自备 key：目录表 + env 注入 + 自建出图 MCP）

v1.10 之前，「引擎用哪个模型、用谁出图」完全隐式：grok CLI 的登录态（`~/.grok/auth.json`）、`~/.grok/config.toml`、以及玩家 shell 里的 `XAI_API_KEY` 之类的环境变量。要换成自备服务，玩家得离开游戏去改文件或设变量，改完也没有任何界内反馈；图片侧更彻底——CLI 的图像通道只认 xAI 自家端点（`features.image_gen` 只有开关与模型名覆盖），第三方服务在协议上根本没有入口。本裁决把这件事变成应用里可配置、可验证、可撤销的一等公民，四件事。其一，**对话侧走 CLI 自带的 BYOK 通道，不自己实现**：凭据 → `GROK_MODELS_BASE_URL` + `XAI_API_KEY` + `GROK_DEFAULT_MODEL` 三个环境变量（名字以 grok CLI 文档 `11-custom-models.md` 的「Custom Models Endpoint」段为准），spawn 时合并成 `{...process.env, ...credentialsToEnv(creds)}`——**我们的值优先**，因为 GUI 里填的就是玩家此刻想让引擎用的。第 0 步实证（临时 HOME 无登录态 + 本地 mock 端点）确认这条路在 `grok agent --always-approve stdio` 下真的成立：`GET {base}/models`、`POST {base}/chat/completions`（`model` = `GROK_DEFAULT_MODEL`）、`session/new` 回该模型，全程不需要 `grok login`；副作用只有一条无害的会话标题请求（打 `{base}/responses`，用 CLI 自带默认模型名，第三方端点多半 404，失败只留一条 stderr）。其二，**图片侧自建 MCP 工具**：`server/media-mcp.mjs`（零依赖 stdio JSON-RPC）暴露 `bunkiten-media__generate_image`，自己读凭据、`POST {baseUrl}/images/generations`、自己落盘到 `presets/<剧本 id>/assets/…`；挂在会话的 `mcpServers` 上（**只有 `image.mode === "byok"` 才挂**，第 0 步实证：`session/new` 与 `session/load` 都认这个字段、子进程 cwd = 会话 cwd、env = 父进程 env ∪ 我们给的变量）。为什么不选另外两条路：服务端在收到 `美术：…` 指令时抢先出图、让引擎走缓存命中——覆盖不全（游戏内首现背景没有客户端指令可拦，那是引擎在回合中间自己决定要画的）；改写 `~/.grok/config.toml` 挂 MCP——要合写玩家的全局配置、要 TOML 读写、失败会污染他所有 CLI 会话。引擎侧只加一句契约（SKILL【美术】「出图工具优先（硬规则）」）：先 `search_tool` 找 `bunkiten-media__generate_image`、`use_tool` 调它（第 0 步实证：MCP 工具不进模型直接工具表，必须经这两个元工具，catalog 键是 `server__tool` 形态），拿到 `ok` 直接出【图】标记、**不再调内置 `image_gen`**；工具不在或失败才回退内置；两者都不行就静默跳过。其三，**服务目录是数据表，不是适配器**：`shared/providers.mjs` 一张 `{id, label, kind, baseUrl, models, imageModels?, note?}` 表同时喂 GUI 两个下拉与服务端校验（`PROVIDER_IDS` 由它派生），契约 lint ⑦ 组钉住「GUI 不许自带第二份 id 表」；凡说 OpenAI 兼容协议的服务开箱可用，长尾（自建、私有部署、聚合网关）走「自定义」或 one-api / LiteLLM 这类网关——**不引入 provider SDK / AI 框架**：协议差异已被表吸收，流式与 tool-call 编排本来就由 CLI 承担，而 server 树零依赖是本仓既有纪律（新依赖还要过打包白名单）。其四，**凭据落 `~/.bunkiten/credentials.json`（目录 0700 / 文件 0600，临时文件 + rename 原子写）**：刻意不放 GAME_ROOT——开发态它等于仓库根，`state/` 的 gitignore 规则不覆盖新文件，放那里迟早被 git 收走。明文只活在这一个落点与「玩家正在输入」的那一帧：HTTP 出口一律脱敏（`publicView` 只给 `hasKey` 与 `apiKeyMasked` 如 `sk-…4f2a`），不进日志、不进逐轮快照、不进回合日志、不进世界线/剧本导出包；错误信息统一过 `sanitizeErrorMessage` 抹掉明文再上屏。读路径逐键容错、永不抛（坏 JSON / 缺键 / 多余键 / 类型不对都回默认——凭据坏了不该让 server 起不来）。生效路径只有一条：env 在 spawn 时读一次，所以保存后给「立刻重启引擎」（`POST /api/engine/restart`：旧进程退出 → 按当前凭据重建 → 重新握手；回合进行中拒绝，避免截断这一回合的落盘）。

代价：其一，`server/` 树多三个模块（credentials / credentials-probe / media-mcp），入口闭包多一组凭据能力（`buildAcp` 每次 spawn 现读凭据），`acp.mjs` 的工厂多两个注入项（`env`/`mcpServers`）；其二，打包布局多一条 `asarUnpack`（MCP 是被引擎拉起的**子进程**，子进程读不了 asar；命令用 `process.execPath` + `ELECTRON_RUN_AS_NODE=1`，路径由 `mediaMcpPath()` 把 `app.asar` 段换成 `app.asar.unpacked`）——**这条一开始写错了**：只解 `server/media-mcp.mjs` 一个文件，而它相对 import 的兄弟（`config.mjs`/`assets.mjs`/`presets.mjs`→`acp-server.mjs`/`credentials.mjs` 与 `shared/*`）都不在 unpacked 树里，打包态子进程第一步就 `ERR_MODULE_NOT_FOUND`（dev 与当时的打包冒烟都看不见，因为冒烟用的假引擎从不拉 MCP）。修法：`asarUnpack: [server/**, shared/**]` 两整棵树（枚举单文件会在下次改 import 时静默再坏），并给假引擎加 `FAKE_ENGINE_SPAWN_MCP=1` 让打包态冒烟**真的把 MCP 拉起来跑一遍握手**——动了打包布局/主进程就该补跑这条 opt-in 冒烟，这次它正是抓到这个 bug 的地方；其三，契约面新增一组（`shared/providers.mjs` + 四个端点 + `/api/auth` 的 `hasCredentials` + SKILL 的一句硬规则），契约 lint 加 ⑦ 组、文档三处（ARCHITECTURE / AGENTS / README+QUICKSTART）同步；其四，兼容梯子写进了实现（`response_format` 与 `size` 各退让一次、`b64_json` 与 `url` 两种回包都认），不是每家一份适配，但也不是「一行配置通吃所有服务」。

**补记（同日的三处实测）**：其一，**会话标题那一下**——CLI 起会话时会用**它自己的**默认模型名打一次 `{base}/responses`，对第三方端点必然 404（只留一条 stderr）；`GROK_TITLE_REFRESH=0/false` 与覆盖层 `features.title_refresh=false` 三种开关都**无效**，而 `GROK_CONFIG` 的内联覆盖把 `models.session_summary` 指到玩家配的模型**有效**（`/responses` 消失，标题请求改走 `chat/completions` 用同一个模型）。因此 `credentialsToEnv` 在 BYOK + 有模型时多注入一个 `GROK_CONFIG`，只设这一个键。其二，**Anthropic 原生协议（`/v1/messages`）经这条通道支持不了**：CLI 的 `api_backend` 只能来自 `~/.grok/config.toml` 的 `[model.*]`，而覆盖层白名单会丢弃 `model.*`（实测：请求仍是 `chat/completions` + env 的模型）。要用 Anthropic 就走它的兼容网关——这同时把「被否决：逐 provider 手写适配」的边界写清楚了：**只有协议后端不同才需要声明，而那条声明通道在我们约束下不存在**。其三，**出图尺寸的两格**：`size`（通用覆盖，历史语义）与 `sizeBackground`（背景专用，优先于 `size`）——单格覆盖满足不了「立绘 4:5、背景 16:9」这种常见搭配；两格都留空时按类型默认（立绘/封面竖、背景横）。

被否决：**逐 provider 手写适配**（框架/适配层解决的是协议差异，而这里的事实标准已经把差异压到 base_url 与模型名两个字段，写代码只会把「加一个服务」从改数据变成改代码）；**`.env` 支持**（玩家不该为填一个 key 去编辑文件或设环境变量；GUI 即时保存 + 一键重启比环境文件准确，也不污染 shell）；**加密存储 / 系统 keychain**（本机磁盘加密是这一层的第一道防线，而密钥派生要引依赖、要处理「忘了密码」的恢复路径，收益与复杂度不成比例；本机端点本身也只挡跨站浏览器请求、不防本机进程——见 ARCHITECTURE「已知限制」的同款前提）；**多 profile 并行**（一次只激活一套，切换靠重启引擎；并行会引入「哪个 profile 在跑」的状态面，当前没有真实需求）；**把 key 写进 `~/.grok/config.toml`**（合写玩家全局配置、要 TOML 读写、错了会污染他所有 CLI 会话）；**让服务端抢跑出图走缓存**（覆盖不全，见上）。
